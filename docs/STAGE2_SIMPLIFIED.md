# 階段 2：簡中轉繁設計（草案，待確認）

> 狀態：簡中記憶池、OpenCC 轉換、分級、抽查報告已實作；**目前全部為建議模式**，沒有任何自動採用。
> 抽查報告：`docs/reports/s2t-spotcheck-2026-11-04.md`。

## 1. 對照 1.7 組件確認的前提

遊戲語言為繁中時，只會載入繁中與英文：
- Keyed：先查繁中，查不到就直接用英文（`Translator.Translate` → `LanguageDatabase.defaultLanguage`，固定為 English）。
- DefInjected：只注入目前語言的翻譯；沒有繁中就保留 Defs 原本的英文。
- 簡中資料夾完全不會被讀取，遊戲沒有「退回簡中」的機制。

所以「只有簡中」的模組在繁中玩家看來就是英文；簡中必須轉換後寫進翻譯包才有用。「已有繁中翻譯」的判定只看 `ChineseTraditional` 與 `ChineseTraditional (…)` 資料夾，簡中不會被當成已翻譯。

## 2. 簡中來源（記憶池）

收集**所有已安裝**的非官方模組（含未啟用的翻譯補丁）中、模組內任何 `Languages/ChineseSimplified*`（深度 ≤ 3，涵蓋 `1.4/`、`1.5/`、`Common/`、LoadFolders 指定的子資料夾）。本機實測：458 個模組、274,282 筆。

對應方式：Keyed 以鍵名、DefInjected 以「Def 類型:路徑」對應目前的英文條目（資料夾若為舊式複數，例如 `ThingDefs`，也會嘗試單數）。同一條目有多個來源時，優先順序：
1. 模組自帶 → 2. 翻譯補丁 → 3. 疑似機翻來源；
2. 同級中：目前會被載入的資料夾 → 啟用中的模組。

限制：使用 handle 寫法（`stages.Name.label`）的簡中路徑目前對不上我們的索引路徑（`stages.0.label`），會被略過。

## 3. 轉換

依 OpenCC 1.4.2 的 s2twp 流程：
1. 遊戲術語表 → STPhrases（詞組）→ STCharacters（單字），由左至右最長匹配；
2. 台灣化：TWPhrases → TWVariantsPhrases → TWVariants，對連續片段整段處理（例：軟件→軟體、概率→機率、菜单→選單）。

**一對多字**：第 1 步落到「單字轉換」且字典列出其他候選時，記為歧義（例：后→後／后、并→並／併、它→它／牠）。詞組已涵蓋的不算歧義（例：头发→頭髮）。

**遊戲術語表**：取自遊戲本身附帶的官方簡中與官方繁中語言包（`Data/*/Languages/*.tar`），同鍵配對、2–8 字的短詞。分兩類：

| 類型 | 條件 | 用途 | 本機數量 |
|---|---|---|---|
| 同字異體修正 | 官方繁中每個字都在該簡中字的可接受寫法內 | 參與轉換，修正 OpenCC 的一對多選擇 | 94 |
| 用詞不同 | 官方繁中換了用詞（例：炮塔→砲塔、按钮→鈕扣） | **不替換**；只在簡中整段等於該詞時列為校對提示 | 3,499 |

第一版曾把「用詞不同」也拿來做子字串替換，結果出現 机械→器械、按钮→鈕扣、优先→偏好 等錯誤，已改為上表做法。

## 4. 過期判斷（「重新翻譯」）

依證據強度依序檢查，第一個成立的就採用：

| 順序 | 訊號 | 結果 |
|---|---|---|
| 1 | 簡中的佔位符／標記（`{0}`、`<color>`、`(*Tag)`、`\n` 數量）與**目前**英文不一致 | 過期（佔位符不一致） |
| 2 | 簡中檔在該條目前有 `<!-- EN: … -->` 註解（遊戲「產生翻譯檔」與多數工具會寫入），且與目前英文不同 | 過期 |
| 3 | 簡中所在的同一資料夾（例如 `1.5/Languages/`）也有英文，且與目前英文不同 | 過期 |
| 4 | 以上皆無可比對的資料 | 未驗證（不算過期） |

比較英文時會正規化：字面 `\n` 與換行視為相同、連續空白合併、去除頭尾空白。

過期的簡中**不會被丟棄**：它會以「重新翻譯」分級交給 Agent，簡中與轉換結果附在上下文中當參考。

尚未採用的訊號（太弱或不可靠）：檔案修改時間（工坊下載會重設時間）、模組 `supportedVersions`。

## 5. 可信度估計

分數 0–100，只用於排序與顯示，不單獨決定分級。

| 訊號 | 影響 |
|---|---|
| 來源類型：模組自帶 70／翻譯補丁 60／疑似機翻 25 | 基礎分 |
| 新鮮度已確認（EN 註解或同資料夾英文吻合） | +15 |
| 新鮮度未驗證 | −5 |
| 來自未被載入的資料夾（例如舊版本 `1.5/`） | −15 |
| 該來源涵蓋本模組 ≥ 80% 條目（通常代表有人持續維護） | +5 |
| 該來源涵蓋 < 30% | −5 |
| 簡中與英文相同（未翻譯） | −40 |
| 簡中殘留 4 個字母以上的英文單字（不在專有名詞白名單） | −15 |

「疑似機翻」的判定：提供者的 packageId、名稱或作者含 AI、machine、auto translate、GPT、DeepL、Google Translate、机翻、自动翻译、机器翻译等字樣；本工具自己的翻譯包也算。這只是名稱判斷，無法辨認沒有標示的機翻。

## 6. 三層分級（對應你的規格）

| 分級 | 條件 |
|---|---|
| 重新翻譯 | 過期（第 4 節順序 1–3 任一成立） |
| 交給 Agent 校對 | 不過期，但有任一：一對多字、官方術語有多種寫法、整段命中「用詞不同」提示、疑似機翻來源、未翻譯或殘留英文、來自未載入的資料夾、轉換結果驗證失敗 |
| 直接採用 | 其餘：非機翻來源、無歧義、無術語衝突、佔位符驗證通過 |

注意：「直接採用」包含「新鮮度未驗證」的條目（沒有證據說它過期）。若你希望直接採用必須有正面證據，可加一條「新鮮度必須為已確認」的條件。

## 7. 抽查結果摘要（40 個模組、10,535 筆有簡中的條目）

| 分級 | 筆數 | 比例 |
|---|---|---|
| 直接採用 | 7,279 | 69% |
| 交給 Agent 校對 | 2,525 | 24% |
| 重新翻譯 | 731 | 7% |

一對多字是校對的最大來源（1,940 筆）。前幾名都是常見且預設候選幾乎總是正確的字：个→個、了→了、并→並、后→後、它→它、果→果、具→具。

## 9. 抽查中看到、尚未處理的問題

- 英文就是鍵名本身的條目（例如 `CQF_TestDomainExpansion`），多半是作者沒寫英文。目前會被分到「直接採用」，應該改列為校對。
- 模組把中文放在 English 資料夾（例：ChezhouLib）時，「英文」本身就是簡中，比對結果為「未翻譯」。
- OpenCC 不處理部分台灣慣用詞（例：身份→身分、调试→偵錯）。這類要靠術語表（`glossary_add`，階段 2 後半實作）或 Agent 校對。
