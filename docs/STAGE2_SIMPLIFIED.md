# 階段 2：簡中轉繁設計

> 狀態：簡中記憶池、OpenCC 轉換、分級、抽查報告、自動採用設定、術語表、翻譯記憶、掃描快取已實作。
> 抽查報告的 20 筆分級已由使用者確認合理（2026-11-04）。**自動採用預設仍關閉**，需使用者自行在 config.json 開啟。
> 抽查報告：`docs/reports/s2t-spotcheck-2026-11-04.md`（確認前的版本；之後新增的規則見第 9 節）。

## 1. 對照 1.7 組件確認的前提

遊戲語言為繁中時，只會載入繁中與英文：
- Keyed：先查繁中，查不到就直接用英文（`Translator.Translate` → `LanguageDatabase.defaultLanguage`，固定為 English）。
- DefInjected：只注入目前語言的翻譯；沒有繁中就保留 Defs 原本的英文。
- 簡中資料夾完全不會被讀取，遊戲沒有「退回簡中」的機制。

所以「只有簡中」的模組在繁中玩家看來就是英文；簡中必須轉換後寫進翻譯包才有用。「已有繁中翻譯」的判定只看 `ChineseTraditional` 與 `ChineseTraditional (…)` 資料夾，簡中不會被當成已翻譯。

## 2. 簡中來源（記憶池）

收集**所有已安裝**的非官方模組（含未啟用的翻譯補丁）中、模組內任何 `Languages/ChineseSimplified*`（深度 ≤ 3，涵蓋 `1.4/`、`1.5/`、`Common/`、LoadFolders 指定的子資料夾）。本機實測：458 個模組、274,282 筆。

對應方式：Keyed 以鍵名、DefInjected 以「Def 類型:路徑」對應目前的英文條目（資料夾若為舊式複數，例如 `ThingDefs`，也會嘗試單數）。同一條目有多個來源時，優先順序：
1. 模組自帶 → 2. 翻譯補丁 → 3. 疑似機翻來源；
2. 同級中：目前會被載入的資料夾 → 啟用中的模組。

限制：使用 handle 寫法（`stages.Name.label`）的簡中路徑目前對不上我們的索引路徑（`stages.0.label`），會被略過。

## 3. 轉換

依 OpenCC 1.4.2 的 s2twp 流程：
1. 遊戲術語表 → STPhrases（詞組）→ STCharacters（單字），由左至右最長匹配；
2. 台灣化：TWPhrases → TWVariantsPhrases → TWVariants，對連續片段整段處理（例：軟件→軟體、概率→機率、菜单→選單）。

**一對多字**：第 1 步落到「單字轉換」且字典列出其他候選時，記為歧義（例：后→後／后、并→並／併、它→它／牠）。詞組已涵蓋的不算歧義（例：头发→頭髮）。

**遊戲術語表**：取自遊戲本身附帶的官方簡中與官方繁中語言包（`Data/*/Languages/*.tar`），同鍵配對、2–8 字的短詞。分兩類：

| 類型 | 條件 | 用途 | 本機數量 |
|---|---|---|---|
| 同字異體修正 | 官方繁中每個字都在該簡中字的可接受寫法內 | 參與轉換，修正 OpenCC 的一對多選擇 | 94 |
| 用詞不同 | 官方繁中換了用詞（例：炮塔→砲塔、按钮→鈕扣） | **不替換**；只在簡中整段等於該詞時列為校對提示 | 3,499 |

第一版曾把「用詞不同」也拿來做子字串替換，結果出現 机械→器械、按钮→鈕扣、优先→偏好 等錯誤，已改為上表做法。

## 4. 過期判斷（「重新翻譯」）

依證據強度依序檢查，第一個成立的就採用：

| 順序 | 訊號 | 結果 |
|---|---|---|
| 1 | 簡中的佔位符／標記（`{0}`、`<color>`、`(*Tag)`、`\n` 數量）與**目前**英文不一致 | 過期（佔位符不一致） |
| 2 | 簡中檔在該條目前有 `<!-- EN: … -->` 註解（遊戲「產生翻譯檔」與多數工具會寫入），且與目前英文不同 | 過期 |
| 3 | 簡中所在的同一資料夾（例如 `1.5/Languages/`）也有英文，且與目前英文不同 | 過期 |
| 4 | 以上皆無可比對的資料 | 未驗證（不算過期） |

比較英文時會正規化：字面 `\n` 與換行視為相同、連續空白合併、去除頭尾空白。

過期的簡中**不會被丟棄**：它會以「重新翻譯」分級交給 Agent，簡中與轉換結果附在上下文中當參考。

尚未採用的訊號（太弱或不可靠）：檔案修改時間（工坊下載會重設時間）、模組 `supportedVersions`。

## 5. 可信度估計

分數 0–100，只用於排序與顯示，不單獨決定分級。

| 訊號 | 影響 |
|---|---|
| 來源類型：模組自帶 70／翻譯補丁 60／疑似機翻 25 | 基礎分 |
| 新鮮度已確認（EN 註解或同資料夾英文吻合） | +15 |
| 新鮮度未驗證 | −5 |
| 來自未被載入的資料夾（例如舊版本 `1.5/`） | −15 |
| 該來源涵蓋本模組 ≥ 80% 條目（通常代表有人持續維護） | +5 |
| 該來源涵蓋 < 30% | −5 |
| 簡中與英文相同（未翻譯） | −40 |
| 簡中殘留 4 個字母以上的英文單字（不在專有名詞白名單） | −15 |

「疑似機翻」的判定：提供者的 packageId、名稱或作者含 AI、machine、auto translate、GPT、DeepL、Google Translate、机翻、自动翻译、机器翻译等字樣；本工具自己的翻譯包也算。這只是名稱判斷，無法辨認沒有標示的機翻。

## 6. 三層分級（對應你的規格）

| 分級 | 條件 |
|---|---|
| 重新翻譯 | 過期（第 4 節順序 1–3 任一成立） |
| 交給 Agent 校對 | 不過期，但有任一：一對多字、官方術語有多種寫法、整段命中「用詞不同」提示、疑似機翻來源、未翻譯或殘留英文、來自未載入的資料夾、轉換結果驗證失敗 |
| 直接採用 | 其餘：非機翻來源、無歧義、無術語衝突、佔位符驗證通過 |

注意：「直接採用」包含「新鮮度未驗證」的條目（沒有證據說它過期）。若你希望直接採用必須有正面證據，可加一條「新鮮度必須為已確認」的條件。

## 7. 抽查結果摘要（40 個模組、10,535 筆有簡中的條目）

| 分級 | 筆數 | 比例 |
|---|---|---|
| 直接採用 | 7,279 | 69% |
| 交給 Agent 校對 | 2,525 | 24% |
| 重新翻譯 | 731 | 7% |

一對多字是校對的最大來源（1,940 筆）。前幾名都是常見且預設候選幾乎總是正確的字：个→個、了→了、并→並、后→後、它→它、果→果、具→具。

## 8. 自動採用（已實作，預設關閉）

設定在工作資料夾的 `config.json`（預設 `%LOCALAPPDATA%\RimWorldAgentTranslation\config.json`）。**只有使用者能改這個檔案**；MCP 工具不能開啟或放寬條件。

```json
{
  "simplified_auto_adopt": {
    "enabled": false,
    "default": { "enabled": true, "min_trust": 80, "require_confirmed_freshness": true },
    "per_mod": {
      "Ancot.AncotLibrary": { "min_trust": 85, "kinds": ["keyed"] },
      "some.mod": { "enabled": false }
    }
  }
}
```

| 欄位 | 意義 |
|---|---|
| `enabled`（最外層） | 總開關。false 時一律不採用，per_mod 也不生效 |
| `default` / `per_mod.<packageId>` | per_mod 只覆蓋有寫的欄位，其餘沿用 default |
| `min_trust` | 可信度下限（第 5 節） |
| `require_confirmed_freshness` | true：必須有 EN 註解或同資料夾英文證明是最新的；false：「未驗證」也可採用 |
| `kinds` | `["keyed"]`、`["def"]` 或省略（全部） |
| `origins` | `["mod_self"]`、`["patch"]` 或省略（兩者） |

固定規則（不能用設定改變）：只採用「直接採用」分級；疑似機翻來源、驗證失敗、用到 Agent 新增術語的條目永遠不採用；翻譯包中已有的譯文不覆蓋。

使用方式：
- 預覽：`rwat adopt <packageId>`，或 MCP 工具 `adopt_simplified`（apply=false）。回傳可採用數、各略過原因與 10 筆範例。
- 寫入：`rwat adopt <packageId> --apply`，或 `adopt_simplified`（apply=true，未開啟時會拒絕）。寫入工作資料夾，`origin` 標為 `simplified_auto`，`origin_detail` 記錄提供者、資料夾、可信度、新鮮度；之後執行 `build` 才會進翻譯包。
- 撤回：`rwat adopt-revert [packageId]` 移除所有 `simplified_auto` 條目（Agent 提交的不受影響），再 `build`。

實測（Dubs Mint Menus，設定 enabled=true、min_trust 85、kinds keyed）：57 筆有簡中，46 筆寫入、11 筆因校對分級略過；建置後輸出正確；撤回移除 46 筆。

## 9. 術語表、翻譯記憶、快取

**術語表**（`glossary.json`，在工作資料夾）：
- `s2t`：簡中詞 → 繁中詞，參與簡轉繁，優先於官方術語與 OpenCC。至少 2 字（避免單字規則改寫所有文字），譯名不可含簡體字。
- `en`：英文詞 → 繁中譯名，get_batch 每筆的 `terms` 會列出原文中出現的詞（使用者術語優先，其次是官方繁中的 Def 名稱，約數千筆）。
- 來源標記：`builtin`（內建：身份→身分、调试→偵錯）、`user`（CLI `rwat glossary-add`）、`agent`（MCP `glossary_add`）。Agent 不能覆蓋 user 的詞；用到 agent s2t 詞的條目改列校對、不會被自動採用——避免模組文字誘導 Agent 新增術語後影響自動採用。

**get_batch 的 memory**（每筆最多 5 項）：
- `simplified_converted`：簡中轉繁結果，附分級、新鮮度、可信度、問題說明。「重新翻譯」分級會註明只作參考。
- `official_exact`：遊戲官方繁中對**完全相同英文**的譯法。
- `pack_exact`：翻譯包內相同英文的既有譯文。

**query_memory**：以英文或中文子字串查官方繁中、翻譯包、術語表。

**掃描快取**（`cache/scan/<packageId>.json`）：只快取抽取結果，「是否已被其他模組翻譯」每次重新判斷。指紋包含遊戲版本、Assembly-CSharp、啟用清單與順序、每個啟用模組的 About.xml、本模組 Defs／English／Assemblies 每個檔案的大小與時間。限制：依賴模組只改 Defs 而 About.xml 不變時不會察覺；`scan_mod` 一律強制重掃。40 個模組的抽查報告：這次首次執行 9 秒、有快取 4 秒（先前記錄的 1 分 43 秒可能包含系統檔案快取未熱的時間，不全是本快取的效果）。

## 10. 確認後新增的分級規則

- 英文就是鍵名本身（作者沒寫英文）→ 校對。
- 英文原文含中文（模組把中文放在 English 資料夾）→ 校對。
- 用到 Agent 新增的 s2t 術語 → 校對。

重新統計（同 40 個模組）：直接採用 7,184（原 7,279）／校對 2,620（原 2,525）／重新翻譯 731。
